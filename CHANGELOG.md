# Changelog

Phase-level history of VEye V2. **Every commit that changes behaviour adds a line under `[Unreleased]`**
(format and rules: `docs/00-git-and-tracking.md`). Per-area detail lives in `docs/`; slice-by-slice detail in `git log`.

> Phases 0–5 were pushed to GitHub as one squashed snapshot (`504f945` … `a8de53a`), so their entries below are the record;
> git history is per-slice from Phase 6 on.

## [Unreleased]
- **Projects: comments and linked documents (Phase 8, slice 8.4 — backend only)**: `ProjectComment` (a note on a project, or on one of its ریز هدف with `objective` set) and `ProjectDocumentLink` (unique per `(project, document)`, both service- and database-enforced). API: `GET/POST /projects/{id}/comments/` (paginated, newest first) and `DELETE /projects/{id}/comments/{id}/`; `GET/POST /projects/{id}/documents/` and `DELETE /projects/{id}/documents/{id}/`. **Anyone who can read a project may comment on it** — a feed with no human note is a machine log, and restricting discussion to the manager would make it useless for ordinary members — but **only a comment's own author may ever delete it, no exception, not even the project's مدیر or مدیر عامل**, the same rule the plan states for chat messages (§2.6), applied here for consistency. Linking or unlinking a document needs the project's مدیر or a lead, the same governance as any other edit to the project's own content. Both actions write to the existing activity feed (two new kinds each, `comment_removed` and `document_unlinked`, alongside the plan's `comment_added`/`document_linked`, for the same "every add has a matching remove" symmetry `member_removed`/`objective_removed` already have) with no changes needed to 8.3's feed views. `ProjectDocumentLink.document` PROTECTs, so a linked document cannot be deleted out from under the link. Kept in its own migration (`projects/0003`), not `0001`, so `apps.projects` does not depend on `apps.documents` from birth, per the plan.
- **Projects: the activity feed (Phase 8, slice 8.3 — backend only)**: a close clone of `apps/documents/history.py`'s pattern, adapted for a domain that (unlike the document register) is not open to everyone. `GET /projects/{id}/activity/` (one project's own feed; an invisible project is a 404, same rule as `/projects/{id}/`) and `GET /projects/activity/` (the feed across every project the caller may read — `?project=` narrows it further, an id for a project the caller cannot see silently returns nothing rather than leaking whether it exists; `?q=` searches by project name, matching Arabic and Persian letterforms alike). Both share `?kind= ?objective= ?actor= ?days=`. `from_status`/`to_status` are overloaded across event kinds (a `ProjectStatus` pair, an `ObjectiveStatus` pair, or a pair of ISO dates for a due-date change) so `get_..._display()` cannot be used generically; a small per-kind lookup supplies the Persian label only where one applies, blank everywhere else. **Fix in `projects/urls.py`**: `projects/activity/` is registered *before* the router include — the same pitfall `config/urls.py` already documents for pdfgen's bulk-print route, since DRF's default detail pattern (`projects/<pk>/`) would otherwise swallow `activity` as a pk value.
- **Projects: objectives and progress (Phase 8, slice 8.2 — backend only)**: `Objective` (ریزهدف), always with **both an assignee and a deadline** — no unassigned backlog. `assignee` points at the `ProjectMember`, not the `User`, so the database itself refuses an objective assigned to someone outside the project, and removing a member who still owns objectives is a typed 409 (`member_has_objectives`) instead of a silent orphan. API: `GET/POST /projects/{id}/objectives/` (`?status= ?assignee=<id>|me ?overdue=1`), `PATCH/DELETE /projects/{id}/objectives/{id}/`, `POST /projects/{id}/objectives/reorder/`. Creating, editing (title/description/weight/due date/assignee), deleting and reordering need the project's مدیر or a lead of its بخش — **except that an objective's own assignee may change its `status` alone**, without being a manager (an assignee who cannot mark their own work done is a dead feature); a request that touches `status` together with anything else still needs the manager. `completed_at` follows `status` automatically. Status, due-date and reassignment changes are written to the activity feed; edits to title/description/weight are not. **Progress and overdue-ness are derived, never stored**: progress % = `Σweight(DONE) / Σweight(status != CANCELLED)` (`None`, not `0`, while there is nothing live to measure), overdue = `due_on < today AND status NOT IN (DONE, CANCELLED)` — both computed with one annotated query per project list (no query per row, no Celery beat). `/projects/` rows now carry `progress`, `weight_done`, `weight_total`, `objective_count`, `overdue_count`; the list gains `?overdue=1`. A project's own `create` can now seed its objectives in the same request as its members — a half-created project (some members, no plan) cannot exist.
- **Projects: the backbone (Phase 8, slice 8.1 — backend only)**: new `apps.projects` with `Project` (owned by one بخش, unique name per بخش on the normalised key), `ProjectMember` (MANAGER / MEMBER, with a **stored** `is_guest` — "not in this project's بخش" — decided once at add time so history is never reclassified) and `ProjectEvent` (the activity feed: actor name and سمت snapshotted as text, written by the service in the same transaction as the change, never by a signal). API `/projects/` (list/create/detail/edit), `archive/` and `unarchive/`, and `projects/{id}/members/` (add, change role, remove); filters `?section= ?status= ?q= ?mine=1 ?archived=1`. **Visibility is queryset scoping** — a project you may not read is a 404 — for: its members, leads of its بخش or any ancestor, and `manage_organization`. **Editing** needs the project's مدیر or a lead of its بخش (or an ancestor); **creating** needs `create_project` or leading the target بخش. Decided with the owner: the creator becomes the project's مدیر automatically (a guest manager if they are not in that بخش), so there is a manager from the first moment; an **archived project is read-only** (409 `project_archived`) until un-archived, while DONE/CANCELLED stay editable so they can be reopened. Status moves permissively in any direction and every change is recorded. A project always keeps at least one مدیر (409 `last_manager`, race-safe under a row lock). A بخش with projects, and a person on or creator of projects, cannot be deleted (409 with counts). Objectives, progress and the feed endpoints follow in 8.2–8.4.
- **Fix: a missing object is answered in Persian.** `GET /org/nodes/99999/` (and any `get_object_or_404`) used to answer Django's English «No OrgNode matches the given query.»; every such 404 now says «مورد درخواستی یافت نشد.» (`veye_exception_handler`). Found while checking that an invisible project is a 404.
- **Personnel get a place in the chart (Phase 7, slice 7.8)**: the register page («ثبت پرسنل») gains an optional «جایگاه در ساختار سازمان» — a node (indented so the tree still reads), an optional position label and «مسئول این گره». After the account is created the membership is a second request, so a failed placement never reads as a failed registration (and is never silent): the message says the account exists and where to add them later. Below the form, «افراد بدون جایگاه سازمانی» lists everyone with no membership (`/org/people/?unassigned=1`) with a select and «قرار بده» — the quick way to place existing personnel, the importer's included. Without this no بخش would ever have anyone in it. **Fix that this needed:** the register form now stores the national code and mobile number with ASCII digits, exactly as the login page (7.5) sends them; before, someone registered with Persian digits could never sign in.
- **Organisation chart (Phase 7, slice 7.7)**: «ساختار سازمان» at `/organization`, labelled in the sidebar with the **company's own name**. The company is drawn as a building — a framed facade with its name and logo, each حوزه a floor, each واحد a room, each بخش a desk, and a company with no حوزه simply has one ground floor — hand-built in CSS with no library. Drag to pan; zoom with the buttons or Ctrl/⌘ + wheel; «نمای کامل» fits the whole building (it also does so on first load). Every clickable part is a real `<button>` with a spoken label, and «نمای فشرده» swaps the drawing for the plain nested `<ul role="tree">` (for screen readers and very large organisations). Selecting a node opens a side panel: the people in it (initials avatar, name, سمت, «مسئول» badge), and — **only where the server's own `can_*` flags allow it, so a button shown is a request the server accepts** — add a person (name search over `/org/people/`), make/unmake مسئول, remove, add a child, rename, archive/unarchive, delete (with a confirmation that explains archiving instead). Archived nodes are hidden unless «نمایش بایگانی‌شده‌ها». `GET /auth/me/` now also carries `company` (name, logo, whether setup is complete) and the caller's own `memberships` (primary first, active nodes only); the existing keys are unchanged. The sidebar also gains «کارتابل» and «پروژه‌ها» entries, disabled («به‌زودی») until their phases.
- **First-run setup wizard (Phase 7, slice 7.6)**: `/setup` walks a buyer from an empty database to a drawn company chart without a shell — token + company name + the مدیر عامل account (or promoting an existing one, which signs no one in and sends them to the login page), then company name/logo and «آیا شرکت چند حوزه دارد؟», واحدها, بخش‌ها, and «آمادهٔ شروع» with the chart preview and «ورود به نرم‌افزار». **Resumable with no draft state**: every step writes real rows through the ordinary `/org/` API and `Company.setup_step` is only a bookmark, so a refresh, a crash or another browser lands on the right step from `GET /setup/status/` + `GET /org/tree/`; going back is always allowed. A live `<ul role="tree">` preview (`OrgTreeList`, reused by the chart in 7.7) grows beside every step. `proxy.ts` treats `/setup` as public — the server's one-time setup token, not hiding the page, protects bootstrap. While setup is unfinished, the manager sees a «ادامهٔ راه‌اندازی» banner in the app shell, so the wizard can be found again from any browser (and on installs that predate setup). Also: the API client now sends you back to the page you were on after a session expires (`/login?next=…`, was plain `/login`), reads errors nested inside nested serializers (the password rules), and `apiPost` accepts headers; new `lib/organization.ts` (tree building, ancestors/descendants, select options — order-independent, with a company that has no حوزه valid) and `lib/setup.ts` (step routing, validation).
- **New login page (Phase 7, slice 7.5)**: `/login` is rebuilt as a dark, two-column screen — brand and positioning on the right (RTL first) with an animated accent rule and a staggered entrance (CSS keyframes, no animation library, off under `prefers-reduced-motion`), the sign-in card on the left; on a phone the form comes first under a compact brand mark. New dark tokens (`--surface`, `--line`, `--accent`) in `globals.css`; the light app shell is unchanged. **Fixes the page ignoring `?next=`** that `proxy.ts` sets: after signing in it now returns there, accepting only a plain in-app path (no `//host`, `https:`, `javascript:`, backslash or control-character tricks, and never `/login` itself). The national code is normalised to ASCII digits on submit, so an account made by the setup wizard can be signed into from a Persian keyboard. When `GET /setup/status/` says the database has no company and no active مدیر عامل exists, the card offers «شروع راه‌اندازی» instead of the form; where such an account already exists (an install that predates setup) the form stays — otherwise that install would be locked out — and setup is a secondary link. The company name is not shown on the public page: `/setup/status/` deliberately reveals no names. `/setup` itself arrives in 7.6.
- **First-run setup (Phase 7, slice 7.4 — backend only)**: a buyer can now stand VEye up without a shell. `GET /setup/status/` (public: `{needed, has_users, step}` and nothing else), `POST /setup/bootstrap/` and `POST /setup/complete/`. Bootstrap is guarded by a one-time **`VEYE_SETUP_TOKEN`** in `.env` (header `X-VEYE-Setup-Token`, constant-time compared, never in a query string, never echoed, rate-limited per IP by `SETUP_RATELIMIT_RATE`, default 5/m): **unset or empty answers 503** as if the endpoint did not exist (not 403, which would say "keep guessing"), a wrong token is 403, and `prod.py` refuses to start if a token is set but shorter than 32 bytes. Bootstrap creates the company root, the `Company(pk=1)` row, the مدیر عامل (کارفرمایی / لول ۱, every capability, not a Django superuser) and their lead+primary root membership in **one transaction**; the `pk=1` insert — not a lock on users, which Postgres cannot take on rows that do not exist yet — is what makes it impossible to run twice, and two concurrent bootstraps leave exactly one company. The new manager is signed in by the response; the wizard then uses the ordinary `/org/` API under their session. Where users already exist (the importer path) `existing_manager_national_code` promotes an active کارفرمایی لول ۱ — it never sets or reads a password and **issues no session**, so the setup token plus a national code can never be a login. Decided with the owner: `company_name` is required at bootstrap; the manager's password must pass Django's validators (Persian messages); `complete/` needs nothing structural, only `manage_organization` and that setup is not already complete (one conditional UPDATE, so of two concurrent callers exactly one wins). `Company.setup_step` is now a real bookmark: every node, membership or company-profile write moves it in the same transaction while setup is unfinished (no ordering guard — going back is legitimate), so a refresh or another browser resumes at the right step with no draft table.
- **Lead access (Phase 7, slice 7.3 — backend only)**: the org surfaces are now **capability OR lead-of-an-ancestor**. A person the مدیر عامل marked as مسئول (`Membership.is_lead`) of a node can build, rename, move, archive and delete that node and everything below it and manage its people — without holding `manage_organization` / `manage_membership`, and never beyond their own branch. One module, `organization/access.py`, holds the rule; the permission classes, the write endpoints and the new per-node `can_edit` / `can_add_child` / `can_manage_members` flags in `/org/tree/` and `/org/nodes/` all call the same functions, so a button cannot disagree with the server. `OrgAccess` costs **one query per request** (the user's lead memberships) — zero for a capability holder — and everything after is prefix arithmetic on `OrgNode.path`; `led_subtree_q()` gives Phase 8/9 a single-LIKE filter for "inside a subtree I lead". Rules decided with the owner: leads hold full powers over the node they lead *and* below (plan §5.3 as written); re-homing someone (making a node their primary) needs authority over both the new and the current primary node. Chosen here: a move needs authority over the destination too; only memberships on *active* nodes confer authority (an archived node's lead can no longer act there — only someone above can revive it); the company node's name stays with `manage_organization` (it is the company profile). **Guard rails for the two axes**: capabilities are exactly the roll's whatever the memberships (all 9 roll × level × 5 lead scenarios), no `apps/documents` module mentions memberships, and a صفی lead of the whole company still gets 403 on confirm/approve.
- **Memberships and the people directory (Phase 7, slice 7.2 — backend only)**: `Membership` (person × node, `is_lead`, `is_primary`, free-text `position_label`), several per person. Invariant kept by `memberships.py`: **a person with any membership has exactly one primary** (first one is primary automatically, making another primary demotes the old, the only primary cannot be unset, removing it promotes the earliest remaining); each person's writes are serialised by a row lock on the user. API: `/org/memberships/` (read: any signed-in user; write: `manage_membership`; a membership's person and node never change — remove and re-add), `GET /org/nodes/{id}/members/` (leads first), and `GET /org/people/` (`?q=`, `?node=`, `?unassigned=1`). People and members expose name, سمت and places only — never the national code or phone number that `/personnel/` returns. Deactivated people keep their memberships but are hidden unless `?include_inactive=1`; they cannot be added to a node. Nodes with members can't be deleted (`members` joins the 409 counts), and archived nodes can't receive members. **Deleting a person who still has memberships is now a 409 `user_has_memberships`** (before this it would have been misreported as «has documents»). Name search normalises Arabic/Persian letters, digits and Unicode whitespace *in SQL* (no stored copy, no data migration); a test pins the SQL against `normalize_search_term`.
- **Organisation tree (Phase 7, slice 7.1 — backend only)**: new `apps.organization` with `Company` (singleton, `pk=1`) and `OrgNode` — one self-referencing table for شرکت / حوزه / واحد / بخش with a materialised `path` and stored `depth`. A واحد may hang directly under the company (a company with no حوزه is valid). The parent-kind table, the single root and sibling-unique names (on the normalised key, so Arabic and Persian yeh collide) live in the database as constraints; `tree.py` owns everything a CHECK cannot see (path/depth, cycle check on move, delete pre-flight) and checks first so callers get Persian errors. API: `GET /org/tree/` (flat, depth-first, one query; capped by `ORG_TREE_MAX_NODES`, over it two levels + `truncated` and `?parent=` lazy loading), `/org/nodes/` CRUD + `archive/` + `unarchive/`, `/org/company/` and its logo. Reads: any signed-in user. Writes: `manage_organization`. Nothing can create the `Company` row yet — bootstrap arrives in slice 7.4.
- **Three new capabilities**: `manage_organization`, `manage_membership`, `create_project` (کارفرمایی gets all three, ستادی gets `create_project`, صفی nothing; the مدیر عامل gets them automatically). They gate only the coarse "may I use this surface" question and never touch the five document capabilities. **There is deliberately no "read any conversation" capability and there must never be one**: the مدیر عامل is built from `Capability.values`, so it would silently hand that position everyone's private messages. Chat access will be membership-based only (a test pins that no capability name mentions conversations).
- Dev: opening the app on `http://127.0.0.1:3000` now redirects to `http://localhost:3000` (`next.config.ts`). Next blocked its dev resources for `127.0.0.1` (no hydration, so the login form silently reloaded) and the API's host-only session cookies live on `localhost`.
- Designer: after a successful «ذخیره» the app returns to «ساخت مستند» with a «ذخیره شد» message (as V_1.0 did).
- **مدیر عامل** (کارفرمایی لول ۱) now holds every capability (was approve + personnel + PDF only); the one-person-per-step rule still applies to him.

## Phase 6 — history, bulk print, dashboard extras, importer ✅ (docs: `10-phase-6.md`)
- **History screen** (`/documents/history`): revisions tab (filter, family chains, signers, PDF link) + activity tab (audit feed, filters). New `GET /history/revisions/` and `/history/activity/`; register search helpers extracted to `queries.py`. Docs: `10-phase-6.md`.
- **Dashboard extras**: «منتظر اقدام شما» card (`GET /dashboard/awaiting/`, same verdict as the register's buttons) and a recent-activity card.
- **چاپ لیست (bulk print)**: ZIP of already-built official PDFs for ticked rows or the current filter, with a preflight (ready / missing + reason), capped at `BULK_PRINT_MAX_FILES`; never renders. `GET /documents/bulk-print/[preflight/]`.
- **V_1.0 importer** (`manage.py import_v1`): Mongo (env-supplied URI) or a mongoexport file + local `saves/` and `img/` → Postgres, as a Celery job with a stored report; dry-run by default, skip-and-report on collisions, all-or-nothing writes with per-document savepoints, no network downloads; new `IMPORTED` audit event; `pymongo` dependency and a read-only `/import_data` mount.

## Phase 5 — Workflow, signatures, status, public verify ✅ (docs: `09-workflow.md`)
- State machine DRAFT → AWAITING_CONFIRMATION → AWAITING_APPROVAL → UNDER_CONTROL with مرجوع back to DRAFT (reason required, sign-offs cleared),
  one different person per step, row-locked transitions, typed 409s.
- Signer identity from the session; canvas signature pad; server normalises to an opaque PNG and refuses a blank pad.
- Audit trail (`DocumentEvent`), `GET /documents/{id}/history/`; designer shows the return banner + timeline; the designer's «نمایش» was wired.
- Approving a revision obsoletes the previous one and (re)builds PDFs.
- Public `/verify/{code}` page + rate-limited `GET /api/v1/verify/{code}/` (pending documents disclose nothing).
- 50 backend tests (11 mutations each caught), 12 frontend tests; run through the real Celery worker and the browser.
