### Phase 10 — foundation (on main before the parallel work)
- **Parallel Phase 10 work can run side by side.** `docker-compose.yml` host ports come from `BACKEND_HOST_PORT` / `FRONTEND_HOST_PORT` / `POSTGRES_HOST_PORT` / `REDIS_HOST_PORT` (defaults unchanged: 8000/3000/5432/6379), so each git worktree runs its own compose project (`docker compose -p veye_a1 …`) on its own `aN.localhost` host — separate hosts keep the stacks' login cookies apart, which ports alone do not. The dev-only 127.0.0.1 redirect in `next.config.ts` now goes to `FRONTEND_BASE_URL` (default `http://localhost:3000`) instead of a hard-coded address. Settings the Phase 10 slices will read are added up front so the branches do not collide in `base.py`: `PROJECT_DRAFT_MAX_BYTES` (64 KB), `CHAT_ATTACHMENT_MAX_BYTES` (20 MB), `CHAT_ATTACHMENT_MAX_FILES` (5), `CHAT_ATTACHMENT_RATELIMIT_RATE` (20/m) — all in `.env.example`.
- **Fix: the setup wizard kept jumping back to the first حوزه / واحد after every «افزودن».** Root cause: `useApiQuery` threw its data away on every reload, so the wizard showed «در حال بارگذاری...», unmounted, and came back with the بخش step's chosen واحد reset to the first one (and the chosen step, the company-step radio and the org chart's pan/zoom reset too). A reload of the **same path** now keeps the previous answer on screen (`loading` is true only before the first answer; a new `refreshing` flag covers reloads); a **different path** still starts from nothing, so a newly selected node never shows the previous node's members. The rule is a pure function (`lib/query-state.ts`, +6 vitest).
- **Fix: browser extensions no longer break hydration.** Grammarly (and similar add-ons) write `data-gr-*` attributes onto `<body>` before React hydrates, which Next reported as «A tree hydrated but some attributes of the server rendered HTML didn't match». `<html>` and `<body>` in `app/layout.tsx` now carry `suppressHydrationWarning`, which silences attribute mismatches on those two elements only — anything inside the page still warns.

- **Chat: messages (Phase 9, slice 9.2 — backend only)**: `GET/POST /chat/conversations/{id}/messages/`, `DELETE /chat/conversations/{id}/messages/{id}/` and `POST /chat/conversations/{id}/read/`. **Cursor paging on message id** — no COUNT, no offsets: no cursor = the newest page, `?before=<id>` scrolls up, `?after=<id>` polls for newer messages (usually an empty, cheap answer); always oldest-first with `has_more`; `?limit=` (default `CHAT_PAGE_SIZE` 50, capped at `CHAT_MAX_PAGE_SIZE` 200). Sending (≤ 4000 characters, trimmed, Persian 400 when empty) snapshots the sender's name and سمت, moves the conversation's `last_message_*` under a row lock (a real-thread test pins it) and marks the sender's own message read; it is rate-limited per person (`CHAT_SEND_RATELIMIT_RATE`, default 60/m; reads are not). An archived node's channel and a DM with a deactivated person answer **409** (`conversation_read_only` / `user_inactive`). **Delete is a tombstone — the project's first soft delete, deliberately not a pattern**: the row stays in place (`deleted_at`, `deleted_by`) but the API never returns its words (`body: ""`, `is_deleted: true`); **only the sender may delete, no exception — not a lead, not the مدیر عامل**; idempotent; no editing exists. Read marks only move forward and never past the newest message (one conditional UPDATE, race-safe). Conversation rows now carry `unread_count` (other people's live messages after my read mark; system lines, my own and deleted ones never count; a channel never opened counts everything), `my_last_read_message_id` and a `last_message` preview — all annotated into the one list query (no query per row). **System lines**: joining or leaving a node writes «… به گفتگو اضافه شد.» / «… از گفتگو خارج شد.» into its channel in the same transaction, so a group stays legible as people come and go.

API: `GET /chat/conversations/` (newest activity first) and `/chat/conversations/{id}/`. **Access**: a DM is readable by its two people and **nobody else — no capability, no lead, not the مدیر عامل** (an invisible conversation is a 404); a group channel by members of that node and leads of any *active* ancestor, decided from `Membership` at request time so it never drifts; a participant row on a group channel grants nothing (it only holds the read mark). Decided with the owner: (1) **the company channel is open to everyone with a place in the chart** (the strict rule would have admitted only the مدیر عامل); (2) **a node whose channel has messages cannot be deleted** (409 `node_not_empty` now also counts `messages`; archive instead) — an empty channel, or one with only system lines, goes with its node; (3) **an archived node's channel is read-only** (`can_post: false`); (4) a lead's list shows lower channels **only once they have opened them**, so a مدیر عامل's list is not every بخش in the company. A DM whose other person was deactivated stays readable but `can_post: false`.

- **Projects: the activity feed (Phase 8, slice 8.3 — backend only)**: a close clone of `apps/documents/history.py`'s pattern, adapted for a domain that (unlike the document register) is not open to everyone. `GET /projects/{id}/activity/` (one project's own feed; an invisible project is a 404, same rule as `/projects/{id}/`) and `GET /projects/activity/` (the feed across every project the caller may read — `?project=` narrows it further, an id for a project the caller cannot see silently returns nothing rather than leaking whether it exists; `?q=` searches by project name, matching Arabic and Persian letterforms alike). - **Projects: objectives and progress (Phase 8, slice 8.2 — backend only)**: `Objective` (ریزهدف), always with **both an assignee and a deadline** — no unassigned backlog. `assignee` points at the `ProjectMember`, not the `User`, so the database itself refuses an objective assigned to someone outside the project, and removing a member who still owns objectives is a typed 409 (`member_has_objectives`) instead of a silent orphan. API: `GET/POST /projects/{id}/objectives/` (`?status= ?assignee=<id>|me ?overdue=1`), `PATCH/DELETE /projects/{id}/objectives/{id}/`, `POST /projects/{id}/objectives/reorder/`. Creating, editing (title/description/weight/due date/assignee), deleting and reordering need the project's مدیر or a lead of its بخش — **except that an objective's own assignee may change its `status` alone**, without being a manager (an assignee who cannot mark their own work done is a dead feature); a request that touches `status` together with anything else still needs the manager. `completed_at` follows `status` automatically. Status, due-date and reassignment changes are written to the activity feed; edits to title/description/weight are not. **Progress and overdue-ness are derived, never stored**: progress % = `Σweight(DONE) / Σweight(status != CANCELLED)` (`None`, not `0`, while there is nothing live to measure), overdue = `due_on < today AND status NOT IN (DONE, CANCELLED)` — both computed with one annotated query per project list (no query per row, no Celery beat). `/projects/` rows now carry `progress`, `weight_done`, `weight_total`, `objective_count`, `overdue_count`; the list gains `?overdue=1`. A project's own `create` can now seed its objectives in the same request as its members — a half-created project (some members, no plan) cannot exist.

Bootstrap is guarded by a one-time **`VEYE_SETUP_TOKEN`** in `.env` (header `X-VEYE-Setup-Token`, constant-time compared, never in a query string, never echoed, rate-limited per IP by `SETUP_RATELIMIT_RATE`, default 5/m): **unset or empty answers 503** as if the endpoint did not exist (not 403, which would say "keep guessing"), a wrong token is 403, and `prod.py` refuses to start if a token is set but shorter than 32 bytes. Bootstrap creates the company root, the `Company(pk=1)` row, the مدیر عامل (کارفرمایی / لول ۱, every capability, not a Django superuser) and their lead+primary root membership in **one transaction**; the `pk=1` insert — not a lock on users, which Postgres cannot take on rows that do not exist yet — is what makes it impossible to run twice, and two concurrent bootstraps leave exactly one company. The new manager is signed in by the response; the wizard then uses the ordinary `/org/` API under their session. Where users already exist (the importer path) `existing_manager_national_code` promotes an active کارفرمایی لول ۱ — it never sets or reads a password and **issues no session**, so the setup token plus a national code can never be a login. Decided with the owner: `company_name` is required at bootstrap; the manager's password must pass Django's validators (Persian messages); `complete/` needs nothing structural, only `manage_organization` and that setup is not already complete (one conditional UPDATE, so of two concurrent callers exactly one wins). `Company.setup_step` is now a real bookmark: every node, membership or company-profile write moves it in the same transaction while setup is unfinished (no ordering guard — going back is legitimate), so a refresh or another browser resumes at the right step with no draft table.
- **Lead access (Phase 7, slice 7.3 — backend only)**: the org surfaces are now **capability OR lead-of-an-ancestor**. A person the مدیر عامل marked as مسئول (`Membership.is_lead`) of a node can build, rename, move, archive and delete that node and everything below it and manage its people — without holding `manage_organization` / `manage_membership`, and never beyond their own branch. One module, `organization/access.py`, holds the rule; the permission classes, the write endpoints and the new per-node `can_edit` / `can_add_child` / `can_manage_members` flags in `/org/tree/` and `/org/nodes/` all call the same functions, so a button cannot disagree with the server. `OrgAccess` costs **one query per request** (the user's lead memberships) — zero for a capability holder — and everything after is prefix arithmetic on `OrgNode.path`; `led_subtree_q()` gives Phase 8/9 a single-LIKE filter for "inside a subtree I lead". Rules decided with the owner: leads hold full powers over the node they lead *and* below (plan §5.3 as written); re-homing someone (making a node their primary) needs authority over both the new and the current primary node. Chosen here: a move needs authority over the destination too; only memberships on *active* nodes confer authority (an archived node's lead can no longer act there — only someone above can revive it); the company node's name stays with `manage_organization` (it is the company profile). **Guard rails for the two axes**: capabilities are exactly the roll's whatever the memberships (all 9 roll × level × 5 lead scenarios), no `apps/documents` module mentions memberships, and a صفی lead of the whole company still gets 403 on confirm/approve.
- **Memberships and the people directory (Phase 7, slice 7.2 — backend only)**: `Membership` (person × node, `is_lead`, `is_primary`, free-text `position_label`), several per person. Invariant kept by `memberships.py`: **a person with any membership has exactly one primary** (first one is primary automatically, making another primary demotes the old, the only primary cannot be unset, removing it promotes the earliest remaining); each person's writes are serialised by a row lock on the user. API: `/org/memberships/` (read: any signed-in user; write: `manage_membership`; a membership's person and node never change — remove and re-add), `GET /org/nodes/{id}/members/` (leads first), and `GET /org/people/` (`?q=`, `?node=`, `?unassigned=1`). People and members expose name, سمت and places only — never the national code or phone number that `/personnel/` returns. Deactivated people keep their memberships but are hidden unless `?include_inactive=1`; they cannot be added to a node. Nodes with members can't be deleted (`members` joins the 409 counts), and archived nodes can't receive members. **Deleting a person who still has memberships is now a 409 `user_has_memberships`** (before this it would have been misreported as «has documents»). Name search normalises Arabic/Persian letters, digits and Unicode whitespace *in SQL* (no stored copy, no data migration); a test pins the SQL against `normalize_search_term`.
- **Organisation tree (Phase 7, slice 7.1 — backend only)**: new `apps.organization` with `Company` (singleton, `pk=1`) and `OrgNode` — one self-referencing table for شرکت / حوزه / واحد / بخش with a materialised `path` and stored `depth`. A واحد may hang directly under the company (a company with no حوزه is valid). The parent-kind table, the single root and sibling-unique names (on the normalised key, so Arabic and Persian yeh collide) live in the database as constraints; `tree.py` owns everything a CHECK cannot see (path/depth, cycle check on move, delete pre-flight) and checks first so callers get Persian errors. API: `GET /org/tree/` (flat, depth-first, one query; capped by `ORG_TREE_MAX_NODES`, over it two levels + `truncated` and `?parent=` lazy loading), `/org/nodes/` CRUD + `archive/` + `unarchive/`, `/org/company/` and its logo. Reads: any signed-in user. Writes: `manage_organization`. Nothing can create the `Company` row yet — bootstrap arrives in slice 7.4.
- **Three new capabilities**: `manage_organization`, `manage_membership`, `create_project` (کارفرمایی gets all three, ستادی gets `create_project`, صفی nothing; the مدیر عامل gets them automatically). They gate only the coarse "may I use this surface" question and never touch the five document capabilities. **There is deliberately no "read any conversation" capability and there must never be one**: the مدیر عامل is built from `Capability.values`, so it would silently hand that position everyone's private messages.
